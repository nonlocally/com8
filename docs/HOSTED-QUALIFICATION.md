# Installed clients against the hosted bus

The Codex app-server fixture filters ambient session context from its MCP child.
After the seed returns its exact thread UUID, the helper supplies only that UUID
in the disposable installed plugin cache's MCP environment. It preserves the
descriptor's command, arguments and other environment values, then restores
the original bytes during cleanup before uninstall, after provider shutdown
has been attempted. Any shutdown failure keeps qualification failed. This is
explicit fixture context; ordinary hosts without session context still use
the documented CLI-in-session fallback.

`scripts/qualify-hosted.py` checks a reviewed release against the existing
`https://bus.nonlocally.org` gateway. It reuses the provider, archive and owned
process helpers from [the two-device gate](FLEET-PROVIDER-QUALIFICATION.md).
It does not start a fixture broker or change the hosted service.

This is an operator qualification tool, not the normal installation procedure.
People install COM8, accept their private invitation, and tell their agent what
they want to do. See [the bus guide](BUSES.md).

## What the two modes prove

Run each mode with new, explicitly disposable authenticated provider homes:

| Mode | Actual provider work | Additional checks |
| --- | --- | --- |
| `general` | A Claude agent publishes itself through its installed plugin. A Codex agent starts without publishing, introduces itself through an actual model send, then sends a marked challenge. Claude returns the exact payload through its installed reply tool. | The Codex identity never appears in bus membership, its reply is queued to the same thread, and its original device/session identity is preserved. |
| `private` | Both models join an existing operator-approved fixture bus. Claude sends a challenge to dormant Codex; the same Codex thread resumes and replies. Codex then sends a different challenge and Claude replies. | An actual Codex send is rejected while the Claude recipient has left the bus. Claude rejoins with the same identity before the successful exchanges. |

Each marked challenge carries 5,478 bytes of generated UTF-8 data, including
newlines, quotes and literal shell characters. Passing requires actual tool
events, exact message bytes, the correct conversation ID, endpoint receipts,
and successful cleanup. An accepted send or queued turn alone is not model
consumption. The general run proves Claude's consumption and a reply queued to
the unpublished Codex sender; the private run proves both models' consumption.

Initial registration is an ordinary-language task: make this existing agent
discoverable with a specified name on a specified bus. The helper checks that
the model discovers the installed plugin, inspects the selected service, and
registers the exact session. It does not supply a registration command or an
explicit MCP call recipe. Challenge turns provide exact generated bytes and
one permitted peer; they test delivery rather than open-ended delegation.

Codex's initial `thread/start` response establishes its UUID. Subsequent
app-server processes resume that exact thread and receive that verified UUID
as `CODEX_THREAD_ID`, the context normally present in a terminal session. The
helper never guesses the newest transcript or registers a replacement agent.
This supplied app-server context is part of the test, not a claim that every
MCP host automatically inherits it.
The approval gate accepts either explicit matching session fields or the
installed plugin's default-self registration for that verified thread; another
target or a conflicting explicit session is refused.

## Ownership

The coordinator runs on the broker host. Its private configuration explicitly
names the existing broker database, its administrator-token file, the reviewed
server ID, and the approved bus. The token stays on that host and is read into
memory; it is never sent to either worker, placed in arguments, or printed.

The coordinator may call only `snapshot`, `invite`, `invite_revoke`, and `revoke`
through the normal public HTTPS endpoint. Invitations last ten minutes, name an
existing account, and grant only the selected bus. Revocation is restricted to
principals recovered from this run's own invitation digests and exact generated
device labels. A lost redemption response can therefore still be cleaned up.
An invitation creation whose response is lost cannot be recovered from its
unknown secret; the run stays failed, explicitly records that unresolved
creation, and estimates its ten-minute expiration from the failed request's
completion. It does not claim every invitation was revoked.

SQLite connections use `mode=ro`. Message evidence queries select only rows
whose sender and recipient both belong to this run. An aggregate count detects
unexpected traffic involving an outside principal without selecting its text.
The helper never writes SQL, changes accounts or access policy, creates a bus,
restarts the broker, or changes its service, proxy, DNS or gateway settings.
The broker may perform its ordinary housekeeping when handling API requests.

There is no bus-delete API. The private mode therefore requires an existing
bus explicitly approved for qualification; it does not create a new bus on
every run. Do not point it at an arbitrary private project bus.

The two device workers own only their prepared disposable homes, one generated
script/state directory each, the fresh provider sessions, and the installed
integrations in those homes. They use `setup --claude|--codex --no-service` from
the reviewed extracted archive. No repository clone is needed. SSH agent
forwarding and inherited agent sockets are disabled. No provider credentials
are copied between devices.

When one device is the coordinator itself, its device definition may explicitly
set `"transport": "local"` and an absolute `"python"` path. The same bounded
three-file bootstrap, protocol, process group and EOF cleanup then run as a
local child, with `SSH_AUTH_SOCK` and `SSH_AGENT_PID` removed. This does not need
SSH authorization to the same machine. The other device still uses ordinary
SSH with existing authentication and strict host-key checking. Omitting
`transport` means SSH; there is no automatic fallback. The distinct physical
device fingerprint check still applies.

Incoming replies start disarmed. After both exact identities exist, the
controller names only the other test identity as an allowed peer. No unrelated
agent is intentionally contacted. Unexpected accepted traffic, extra sends or
replies, denied Codex approvals, or an additional registration fail the proof.
Claude's tool scope and peer constraints are supplied through its ordinary
client controls and fixture instructions; Codex additionally has the existing
exact-call approval gate. A passing run checks the resulting actual tool
events and broker records rather than relying on a model's claim.

Cleanup revokes the run's enrolled devices and unused invitations, confirms
revoked credentials are refused, closes owned provider process groups, stops
only the workers' isolated adapters, uninstalls their isolated integrations,
and removes their leased homes. Evidence stays private. Unconfirmed process
cleanup retains the affected home and makes the result fail. Arrange the same
outer cleanup backstop described in the fleet guide for a prepared home whose
device is never contacted.

The broker keeps normal revoked-device and receipt records for its own
retention rules. The helper does not delete production history to make a
directory look clean.

## Prepare and run

Start with the configuration shape in
[the fleet guide](FLEET-PROVIDER-QUALIFICATION.md#prepare-the-private-run-configuration).
Keep its two reviewed device definitions, archive/runtime paths and aligned
source/checksum. Add these fields to the private mode-0600 JSON file:

```json
{
  "origin": "https://bus.nonlocally.org",
  "mode": "private",
  "bus": "<existing operator-approved fixture bus>",
  "approved_existing_bus": true,
  "server_id": "<reviewed persistent broker ID>",
  "broker_database": "/private/existing-broker/bus.sqlite3",
  "admin_token_file": "/private/existing-broker/admin.token"
}
```

For the general run, use `"mode": "general"` and `"bus": "general"` with
fresh provider homes and fresh evidence paths. Each `recipient_user` must be an
account already configured by the operator. Do not put token values in this
configuration. Both operator files must be private, owned regular files.

The coordinator and both devices must have the same checksum-qualified archive
and extracted runtime. Use a separately reviewed bundle of these three scripts
on the coordinator: `qualify-hosted.py`, `qualify-provider-fleet.py`, and
`qualify-provider.py`. The coordinator streams exactly those files to each
worker; the product itself is installed from the archive.
For a coordinator-local worker, the shared configuration format still requires
a valid `ssh` placeholder, but that value is unused when `transport` is `local`.

```sh
# Reads and validates configuration only. No remote calls or provider requests.
python3 qualify-hosted.py plan /private/hosted-private-run.json

# Only after explicit device/authentication ownership handoff.
python3 qualify-hosted.py run /private/hosted-private-run.json \
  --evidence /private/evidence/hosted-private-run-1 --run-live
```

Run the isolated fixtures on a disposable test host:

```sh
python3 scripts/test-hosted-qualification.py -v
```

Those fixtures need only the four helper/test files and Python's standard
library. They do not contact the network, run a provider, inspect real
authentication or open production state. They do not qualify a hosted run.

## Evidence limits

The report identifies source/archive hashes, provider versions, exact native
sessions, device principals, registration IDs, public HTTPS transport, message
correlation and cleanup. Raw model records remain in private evidence.

This gate does not perform GitHub OAuth, OpenWebUI sign-in, browser-role
qualification, desktop application wake, native SSH routing, or an optional
hosted broker upgrade. Standard certificate chain and hostname verification
remains enabled; there is no insecure TLS mode or substitute private tunnel.

## Hosted broker update plan

An ordinary client release does not require a broker restart when its protocol
and schema are unchanged. Review the broker diff first. Updating the hosted
broker is a separate coordinated operation; this qualification helper never
performs it.

1. Freeze the reviewed release archive and checksum. Stage its immutable
   extracted payload on the broker host, outside any checkout. Validate its
   complete manifest. Keep the currently loaded payload.
2. Record the exact existing LaunchAgent label, loaded path, runner path,
   settings path, state directory and broker ID. Require the loaded path to
   match the owned service file. Do not alter the gateway's other host routes.
3. Make a private, consistent SQLite backup using SQLite's backup API, and keep
   the matching administrator token, private settings, runner and plist in the
   same private rollback directory. Record hashes, never secret contents.
4. Qualify the new broker source with temporary state and a temporary loopback
   port. Do not run two brokers against the live database. Confirm whether any
   schema migration makes rollback require the matching database backup.
5. In the coordinated restart window, invoke the reviewed
   `scripts/install-bus-hub.py` with `--source <extracted-runtime>/vendor`, the
   **existing** `--state` and `--settings` paths, and the existing port. This
   operator script is supplied separately; it is not included in the normal
   installed archive. It replaces the exact existing hub LaunchAgent and
   restarts that service, so it must never be used as a speculative probe.
6. Confirm the loaded source, persistent broker ID, authenticated local health,
   public gateway health/admission, retained enrollments and a scoped message
   proof. Save the exact result before calling the update complete.
7. If qualification fails, stop only the owned hub service, restore its saved
   runner/plist and previous immutable source, and restart it. Restore the
   matching state backup only when the reviewed migration requires it; do not
   overwrite newly accepted user messages casually. Confirm health and broker
   identity again. A restore that would discard accepted work requires a
   separate recovery decision.

The operator fills in concrete private paths and reviews the source/schema
delta before executing this plan. A passing client test is not an authorization
to replace a live service.
