# Hub-owner registration limits

The broker rejects new or reactivated registrations with `code: limit` and
`agent registration limit reached` when an active quota is full. A new agent
row also requires retained-row capacity. Leaving a bus does not release active
registration quota. Retirement releases active capacity and preserves history;
an existing retired row can reactivate its exact ID only within the active cap.

The hub owner may set `BUS_REGISTRATION_LIMITS` in the broker process environment
as one complete JSON object. The macOS hub runner generated by
`scripts/install-bus-hub.py` also forwards this JSON-valued key from its existing
private hub settings file. Clients cannot set the policy through requests.

| Field | Default | Maximum owner setting |
| --- | ---: | ---: |
| `active_per_principal` | 128 | 8192 |
| `active_total` | 4096 | 65536 |
| `retained_per_principal` | 1024 | 32768 |
| `retained_total` | 32768 | 262144 |

All four fields are required when the override is present. Values must be
positive JSON integers; zero is not an unlimited mode. Booleans, floats, strings,
unknown or duplicate keys, inconsistent bounds, and input over 2048 bytes fail
startup before state or administrator credentials are opened or created.
Per-principal values cannot exceed their corresponding totals, and active
values cannot exceed their corresponding retained values. Absent configuration
preserves the defaults. Configuration is captured at broker construction.

An example that doubles each default, as it would appear in the hub's private
settings file:

```json
{
  "BUS_REGISTRATION_LIMITS": {
    "active_per_principal": 256,
    "active_total": 8192,
    "retained_per_principal": 2048,
    "retained_total": 65536
  }
}
```

Choose values from the hub's own counts of active and retained registrations,
per principal and in total. The policy is read once, when the broker starts, so
a new value takes effect at the next restart. To check a value beforehand, pass
the policy object, serialized as JSON text, to
`bus_broker._registration_policy`; it raises `ValueError` for anything the
broker would refuse at startup.

A hub runner generated by an earlier `scripts/install-bus-hub.py` forwards a
fixed list of setting names that does not include this one. Regenerate the
runner, or add `BUS_REGISTRATION_LIMITS` to the runner's list of JSON-valued
names, so that the setting reaches the broker.

Raising these limits changes no database schema, credentials, ownership checks,
service epochs, request deduplication, retirement or reactivation authorization.
The existing durable service-fence count uses the retained limits as before;
no fence or active-generation replay key is evicted to create room. One
heartbeat or device poll may name as many registrations as the per-principal
active bound, and never fewer than 128, the number a client sends in one
request. HTTP body, message, pending-work and service-request-history bounds
remain unchanged. Lowering a quota does not delete or retire registrations;
existing exact active IDs may still refresh, heartbeat and receive, while new or
reactivated allocations can be refused.

The setting has no effect beyond the bounds described here. A hub that does not
set it behaves as before.
